# vantage-spacetimedb

SpacetimeDB persistence backend for the [Vantage](https://github.com/romaninsh/vantage)
framework — **incubating**, and excluded from the workspace like `vantage-aws` and
`vantage-kubernetes`.

[SpacetimeDB](https://spacetimedb.com) is a relational database that is also the
application server: a WASM module holding the schema and the reducers runs *inside*
the database, and clients subscribe to SQL queries and are then pushed every
change. That makes it the one backend where push is the product rather than a
bolt-on, and the strongest available exercise of Vantage's change-subscription
contract — row-level deltas **and** server-side filtering.

## Why not `spacetimedb-sdk`?

The official Rust SDK is the right tool for an application that talks to one known
module, and this crate deliberately does not use it.

Its documentation opens by stating it *"depends on a set of module-specific
definitions autogenerated by the SpacetimeDB CLI"*, and the types a dynamic client
would have to implement — `SpacetimeModule`, `DbConnection`, `DbUpdate`,
`TableUpdate` — live in a `#[doc(hidden)]` `__codegen` module carrying an explicit
*"may change incompatibly without a major version bump"* warning.

The blocker is structural, not cosmetic: codegen happens per module at build time,
whereas a Vantage datasource is named in YAML **at runtime**. There is no point at
which the schema is known early enough to generate anything. So this crate owns its
connection and uses the official crates for the wire format only — `spacetimedb-lib`
for module definitions, `spacetimedb-sats` for values.

## Capabilities, honestly

SpacetimeDB's SQL has no `ORDER BY`, `OFFSET`, `GROUP BY`, `IN` or `LIKE`. It does
have `LIMIT` and `COUNT(*)`. Subscriptions are narrower still: whole rows from a
single table or view, `WHERE` only, at most a two-table indexed `JOIN`.

So this driver filters and counts server-side, and **refuses** to sort, search or
paginate — it does not emulate them over a materialised set. `add_order` returns
`Unsupported` rather than quietly downloading the table and sorting in memory.

That is a deliberate choice. Emulation makes a capability flag misleading in the
awkward direction: `can_order: false` while ordering appears to work, so a
consumer cannot tell a cheap server-side sort from a full-table download. A
caller that checks the flags first — as the contract asks — never sees the
refusal at all. The practical consequence is that a grid over a SpacetimeDB table
shows rows in the server's natural order and its sort headers are inert. That is
the truth about this backend.

Aggregates a screen wants must be materialised by the module into a rollup table
or computed in a view; there is no `GROUP BY` to lean on.

## Writes need the database owner, not just a token

SpacetimeDB restricts SQL `INSERT`/`UPDATE`/`DELETE` to the database **owner**. A
perfectly valid token belonging to any other identity is refused with *"not
authorized to run SQL DML statements"*.

So the write capabilities key off ownership, established once per factory by
comparing the `spacetime-identity` response header against the `owner_identity`
from `GET /v1/database/:db`. Deciding from "is a token configured" would advertise
writes that always fail. If the check itself cannot be completed the driver
assumes read-only, because over-claiming is the worse error.

For writes by anyone else, call a **reducer** — which is the path a module
sanctions anyway, since reducers enforce its own rules and raw DML bypasses them.

## The change feed

`watch_vista` subscribes over the v2 BSATN WebSocket, and the vista's conditions
go **into the subscription query itself**. SpacetimeDB maintains that
subscription incrementally, so a row that changes *out of* the filtered set
arrives as a delete. Set membership is therefore correct by construction: no
re-read per notification (as the SurrealDB driver needs), and no whole-set reload
(as Postgres needs).

The wire format has no update event — a changed row is a delete plus an insert of
the same key in one transaction — so this driver pairs them by id and emits
`VistaChange::Updated`. Getting that wrong shows up as rows flickering out of and
back into a grid.

The socket asks for `?compression=None`; the host defaults to Brotli, and reading
a compressed feed would mean carrying a decompressor for no benefit at this size.

## Two traps this driver handles for you

**Event tables.** SpacetimeDB `event` tables insert and delete their rows inside the
same transaction — they exist only long enough to broadcast. A grid over one would
be permanently empty, and the insert/delete pair would be misread as an update. The
factory refuses them with a message naming the cause.

Detecting them needs module-schema **v10**; the flag does not exist in v9. This crate
requests v10 and falls back to v9, reporting the lost capability through
`ModuleSchema::event_detection()` instead of silently guessing.

**Wide integers.** SATS integers wider than 64 bits are surfaced as `string`. A
silently truncated identifier is worse than a textual one. Relatedly, this driver
speaks BSATN rather than the older JSON protocol, which encodes every SATS integer
as a JSON number and so loses precision above 2^53.

## Running the tests

Offline tests decode fixtures captured verbatim from a real host, so they need
nothing installed:

```sh
cargo test --manifest-path vantage-spacetimedb/Cargo.toml
```

The manifest path is not decoration. This crate is in the workspace's `exclude`
list while it incubates, so a bare `cargo test` at the repository root builds
the workspace and never reaches it — reporting a pass that says nothing about
this code.

Live tests need a host. The CLI on crates.io is far behind the server, so install it
from the matching release tag:

```sh
docker run -d --name stdb -p 3000:3000 \
    clockworklabs/spacetime:v2.7.0-hotfix3 start --listen-addr 0.0.0.0:3000

cargo install --git https://github.com/clockworklabs/SpacetimeDB \
    --tag v2.7.0-hotfix3 spacetimedb-cli --locked

# `login` needs a TTY; for a local host, mint an identity over HTTP instead
TOKEN=$(curl -s -X POST http://127.0.0.1:3000/v1/identity | jq -r .token)
spacetimedb-cli login --token "$TOKEN"

cargo test --manifest-path vantage-spacetimedb/Cargo.toml --test live -- --ignored
```

If you mount a data volume, `chown` it first — the image runs as uid 1000
(`spacetime`) and cannot write a root-owned directory.
